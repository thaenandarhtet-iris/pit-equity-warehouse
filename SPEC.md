## 1. What this project proves

Most "backtest-ready" datasets leak future information. A fundamental value for Q3 is usually stamped with the quarter-end date (Sep 30), but the market doesn't learn it until the 10-Q is accepted by the SEC weeks later. Restatements make it worse: a naive dataset shows the corrected number as if it had always been known.

This warehouse builds **point-in-time (PIT)** daily features for a survivorship-bias-free equity universe, where every value is keyed on the moment it became publicly available. It then builds a deliberately **naive** version of the same features and measures how much the naive version leaks.

**Headline result the README must deliver** (computed by script, never hand-typed):
- % of naive (date, security, metric) rows that use information not yet public
- median days of look-ahead in the naive version
- number of restated values the PIT version handles correctly
- as-of join performance: DuckDB `ASOF JOIN` vs two slower alternatives

## 3. Data sources

### 3.1 SEC EDGAR (free): fundamentals and filing timestamps
- **Ticker → CIK map:** `https://www.sec.gov/files/company_tickers.json`
- **Company facts (all XBRL facts for a company):** `https://data.sec.gov/api/xbrl/companyfacts/CIK##########.json` (CIK zero-padded to 10 digits). Each fact has `val`, `end`, sometimes `start`, `fy`, `fp`, `form`, `filed` (a date), `accn` (accession number), and sometimes `frame`.
- **Submissions (filing metadata):** `https://data.sec.gov/submissions/CIK##########.json`. Contains per-filing `accessionNumber`, `form`, `filingDate`, and **`acceptanceDateTime`**. Older filings may be in additional files listed under `filings.files`; fetch those too.
- **Join key:** `accn` (facts) = `accessionNumber` (submissions). This gives each fact an acceptance timestamp, which is more precise than the `filed` date.
- **Fair access rules:** SEC requires a descriptive `User-Agent` header with a name and contact email, and limits clients to 10 requests/second. Read the UA from env var `SEC_USER_AGENT` (never hardcode my email). Throttle to 8 req/s with a simple token bucket. Retry 429/5xx with exponential backoff and jitter, max 5 tries.
- **Caching:** save every raw response under `data/raw/sec/{endpoint}/CIK##########.json`. Skip the download if the cache exists unless `--refresh` is passed. All downstream steps read from cache, so the pipeline is reproducible offline.

> **Verify in Phase 1 (important):** the timezone of `acceptanceDateTime`. It's formatted with a trailing `Z`, but check 3–5 filings against the "Accepted" time shown on each filing's EDGAR index page (displayed in Eastern time) to confirm whether the value is truly UTC or Eastern time labeled as UTC. Record the finding with evidence in `docs/decisions.md`. Getting this wrong shifts availability by hours and can move a filing to the wrong trading day.

### 3.2 Prices: Tiingo EOD (free tier or low-cost plan; budget cap $30/month)
- Endpoint: `https://api.tiingo.com/tiingo/daily/{ticker}/prices?startDate=...&endDate=...` with token from env var `TIINGO_API_KEY`.
- Fields of interest: `date`, `open`, `high`, `low`, `close`, `volume`, `divCash`, `splitFactor`, plus vendor `adjClose`.
- Ticker metadata/coverage: Tiingo publishes a supported-tickers file with start/end dates, which should include delisted names. **Verify** that delisted tickers are available on my plan before relying on them, and check current free-tier request limits. Cache per ticker under `data/raw/prices/{ticker}.json`.
- If Tiingo can't serve delisted names on an affordable plan, stop and tell me at the Phase 2 checkpoint with options. Do not silently switch to a source without delisted coverage (e.g., yfinance), because that would reintroduce survivorship bias, which is the point of the project.

### 3.3 Universe: historical S&P 500 membership
- Preferred source: a public historical S&P 500 constituents dataset with add/remove dates (for example, the `fja05680/sp500` GitHub repo). **Check its license** and cite it in the README. If the license is unclear, tell me at the checkpoint.
- Build a reproducible sample of **~200 securities**, 2015-01-01 to the latest available date: ~170 that were members at any time plus **at least 30 that left the index or delisted during the window**. Use a fixed random seed stored in config.
- Ticker reuse is real (a ticker can belong to different companies over time). Key securities on **CIK**, not ticker. Model ticker history in `dim_security` as **SCD Type 2** (`valid_from`, `valid_to`, `is_current`).

### 3.4 Trading calendar
- Use `exchange_calendars` (XNYS) to generate trading sessions with open/close times in UTC. Write to `dbt/seeds/trading_calendar.csv` via a script, so dbt has no Python dependency at build time.

## 6. Core logic (read carefully: this is where the project earns its credibility)

### 6.1 Availability rule
- `available_ts` = the filing's `acceptanceDateTime`, converted to UTC (after the Phase 1 timezone check).
- `available_date` = the **first trading session whose market open (09:30 ET) is strictly after `available_ts`**. A filing accepted at 16:05 ET on a Tuesday becomes usable on Wednesday. A filing accepted at 08:00 ET on Wednesday is usable on Wednesday. Filings over a weekend or holiday roll to the next session.
- This is deliberately conservative. Document the rule and why in `docs/decisions.md`.

### 6.2 Concept mapping
Companies tag the same idea with different XBRL concepts. Seed `concept_map.csv` with columns `metric, taxonomy, tag, priority, period_type` where `period_type` is `duration` or `instant`. Starter set (extend if needed, keep it small):

| metric | tags (priority order) | period_type |
|---|---|---|
| revenue | `Revenues`, `RevenueFromContractWithCustomerExcludingAssessedTax`, `SalesRevenueNet` | duration |
| net_income | `NetIncomeLoss` | duration |
| eps_diluted | `EarningsPerShareDiluted` | duration |
| total_assets | `Assets` | instant |
| total_liabilities | `Liabilities` | instant |
| stockholders_equity | `StockholdersEquity` | instant |
| shares_outstanding | `dei:EntityCommonStockSharesOutstanding` | instant |

For each (CIK, metric, period), pick the highest-priority tag present. Log how often each fallback tag gets used (this goes in the README data notes).

### 6.3 Discrete quarters (a classic gotcha)
- 10-Q flows (income-statement items) are often reported **year-to-date**: the Q2 10-Q may carry a 6-month value, Q3 a 9-month value. And there's no Q4 10-Q at all; Q4 lives inside the 10-K's full-year number.
- Classify duration facts by `end - start` in days: ~80–100 → quarter, ~170–190 → 6M YTD, ~260–280 → 9M YTD, ~350–380 → fiscal year.
- Prefer directly reported 3-month values. Derive missing quarters by subtraction (Q2 = 6M − Q1, Q3 = 9M − 6M, Q4 = FY − 9M).
- **A derived value's `available_ts` is the max of the inputs' `available_ts`.** Q4 can't be known before the 10-K. Flag derived rows (`is_derived = true`).
- EPS can't be derived by subtraction (share counts change). Use reported quarterly EPS only; leave derived Q4 EPS null and document it.
- Instant (balance-sheet) facts need none of this.

### 6.4 Versions and restatements
- The same (CIK, metric, period) can appear in multiple filings: the original 10-Q, then again as a prior-year comparative in later filings, sometimes with a different (restated) value.
- Keep **every version** in `int_fundamentals__versions` with its own `available_ts` / `available_date`. Never deduplicate to "latest value wins" before the PIT step.
- `is_restatement = true` when a version's value differs from the earliest known version of the same period beyond a tolerance (relative 1e-6).

### 6.5 The PIT snapshot rule (second gotcha)
For a security, metric and trading date `t`, the PIT value is:
1. Among all versions with `available_date <= t`, find the **latest fiscal period** (max `period_end`).
2. For that period, take the version with the latest `available_ts` that is still `<= t`.

Why the two steps: a 10-K re-reports last year's numbers as comparatives. A plain "most recently filed fact" as-of join would sometimes grab a comparative for an older period and make the feature jump **backward** in time. Build a fixture that reproduces this and a test proving the PIT model doesn't regress to an older period.

**Implementation:** precompute a snapshot event table where each row is "as of `available_date`, the state for (security, metric) is (period_end, value)", applying the two-step rule, then use DuckDB `ASOF LEFT JOIN` from the daily universe grid onto the event table. That `ASOF JOIN` is the primary path benchmarked in section 9.

TTM metrics (revenue_ttm, net_income_ttm) = sum of the last 4 discrete quarters **as known at `t`**, each quarter using its own PIT version. Null if fewer than 4 quarters are known.

### 6.6 Prices and corporate actions
- Store raw `close`, `divCash`, `splitFactor` from the vendor.
- Back-adjusted price series are themselves a form of look-ahead (history changes after future splits). So `fct_prices_daily` exposes raw close plus a **daily total return** computed only from information available that day:
  `ret_t = (close_t * split_factor_t + div_t) / close_{t-1} - 1`. Verify the exact split convention against Tiingo's docs and a known split (e.g., AAPL 4:1 in Aug 2020, NVDA 10:1 in Jun 2024) and log it.
- **Reconciliation test** (same idea as an MRR bridge): compound my daily returns into a cumulative series and check it matches the vendor's `adjClose` ratio within a small tolerance for every security. List any mismatches; don't hide them.

### 6.7 Market-cap-based features
`market_cap_t = close_t × shares_outstanding (PIT)`. Then `pe_ttm = market_cap / net_income_ttm` (null if net income ≤ 0), `pb = market_cap / stockholders_equity` (null if equity ≤ 0), `debt_to_equity = total_liabilities / stockholders_equity`. Keep the feature set this small; the project is about correctness, not feature count.

## 7. dbt models

**staging/** (one model per source, rename/cast only)
- `stg_sec__facts`, `stg_sec__filings`, `stg_prices__daily`, `stg_universe__membership`, `stg_calendar__sessions`

**intermediate/**
- `int_filings__availability`: accession → `available_ts`, `available_date`
- `int_facts__mapped`: facts joined to `concept_map`, best tag per (CIK, metric, period)
- `int_facts__discrete_quarters`: section 6.3
- `int_fundamentals__versions`: every version with availability and restatement flag (section 6.4)
- `int_fundamentals__snapshot_events`: section 6.5 events

**marts/**
- `dim_security`: SCD Type 2 on ticker per CIK
- `fct_universe_daily`: (trade_date, security_id) for members on each date, including later-delisted names
- `fct_prices_daily`: raw close, daily total return
- `fct_features_daily`: PIT features (section 6.5–6.7), one row per (trade_date, security_id), plus a `source_available_date` column per metric for auditability
- `fct_features_daily_naive`: same features, deliberately leaky: values keyed on `period_end` and always using the latest version. Add a header comment explaining it exists only for comparison.
- `rpt_leakage_summary`: naive vs PIT comparison (section 9 metrics)

Use `materialized: table` for marts and intermediates. Keep staging as views.

## 8. Tests

### 8.1 dbt tests (aim for ~40+, every one meaningful)
- Generic: `unique` / `not_null` on all keys, `relationships` from facts to dims, `accepted_values` for `metric` and `period_type`.
- Singular (in `dbt/tests/`):
  - `assert_no_lookahead.sql`: zero rows in `fct_features_daily` where any `source_available_date > trade_date`. **This is the headline test.**
  - `assert_snapshot_never_goes_backward.sql`: for each (security, metric), the PIT period_end never decreases over time.
  - `assert_universe_includes_delisted.sql`: at least 30 securities in the universe have a last trading date before the end of the window.
  - `assert_returns_reconcile_to_vendor.sql`: section 6.6 reconciliation within tolerance.
  - `assert_derived_q4_after_10k.sql`: every derived Q4 has `available_ts >=` its 10-K acceptance.
  - `assert_one_row_per_security_day.sql` on `fct_features_daily`.

### 8.2 pytest
- SEC client: throttling respects the rate (time a burst against a fake clock), User-Agent header is set, cache hit skips the network.
- Discrete-quarter derivation on fixture data, including a YTD 10-Q and a 10-K.
- Availability rule edge cases: after-close acceptance, pre-open acceptance, Friday after close, holiday.
- PIT snapshot: the 10-K comparative fixture from section 6.5 does not make the value go backward.
- **Test the test:** run the `assert_no_lookahead` logic against `fct_features_daily_naive` and assert it finds violations (count > 0). If the leakage test can't catch the naive model, it's not testing anything.

### 8.3 CI (`.github/workflows/ci.yml`)
On every push and PR: `uv sync`, `ruff check`, `pytest`, then `dbt seed && dbt build` against the committed fixtures (no network, no secrets). Cache uv.
